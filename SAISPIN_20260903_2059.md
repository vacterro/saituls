# SAISPIN

## Orphaned CPU Watchdog for SAITULS

**Status:** DESIGN
**Host:** Windows / SAITULS
**Mode by default:** DRY-RUN
**Purpose:** detect abandoned processes that continuously burn CPU without useful work.

---

## 1. Цель

**SAISPIN** — фоновый watcher для обнаружения подозрительных процессов, которые длительное время жрут CPU после исчезновения породившего их процесса.

Основные цели:

* находить осиротевшие тесты, shell/python workers, CLI-агенты, build-процессы и другие зависшие процессы;
* отличать нормальную длительную нагрузку от реального spin-loop;
* не реагировать на кратковременные CPU spikes;
* не убивать обычные orphan-процессы только потому, что их parent исчез;
* уведомлять пользователя через tray-механизм SAITULS;
* при явно включённом `auto-kill` завершать только процессы, для которых одновременно доказаны:

  * orphan state;
  * sustained CPU spin.

Главный принцип:

> **Orphan ≠ kill. Spin ≠ kill.
> Auto-kill разрешён только для orphan + sustained-spin.**

По умолчанию SAISPIN работает в **dry-run** режиме: обнаруживает, логирует и уведомляет, но ничего не завершает автоматически.

Дата наблюдения: **03.09.2026**

Процесс:

`cline.exe`, PID `5100`

> busy-loop после потери IPC/parent lifecycle.

Лечение:

`kill cline.exe`

Повторное открытие Cline самостоятельно создаёт новый исправный hub.

Процесс:

`python.exe`, PID `30976`

Команда относилась к Python heredoc/script, который изменял:

`tests/test_app.py`

Состояние:

* parent `bash`, PID `30564`, уже отсутствовал;
* процесс продолжал загружать примерно 100% одного ядра;
* CPU time около `19378 s`;
* полезная работа давно закончилась.

`kill python.exe`

### Контрпример — orphaned pytest

Процессы:

`pytest`, PID `3116` / `5572`

Parent-процессы также отсутствовали.

Однако:

* CPU delta за контрольный интервал ≈ `0`;
* процессы находились в sleeping/idle состоянии;
* постоянного spin-loop не было.

Следовательно:

> Сам факт отсутствия parent-процесса не является основанием для завершения процесса.

Такие процессы SAISPIN не должен автоматически трогать.

## 3. Detection Model

SAISPIN использует несколько независимых сигналов.

### 3.1 CPU sampler

PowerShell делает два замера накопленного:

`Process.CPU`

с интервалом:

`3 seconds`

CPU usage одного logical core вычисляется как:

```text
cpu_percent_core = ((cpu_after - cpu_before) / sample_seconds) * 100
```

Пример:

```text
delta CPU = 2.9 sec
sample window = 3 sec

usage ≈ 96.7% одного ядра
```

Порог `hot/spin candidate`:

```text
CPU > 80% одного logical core
```

Один такой замер сам по себе ничего не доказывает.

---

## 4. Sustained Spin Detection

История хранится между запусками watcher.

State-файл содержит process identity и историю наблюдений.

Process identity:

```text
PID + Process StartTime
```

Не использовать только PID.

Это защищает от PID reuse после завершения старого процесса.

Пример записи:

```json
{
  "30976:2026-09-03T12:20:31Z": {
    "pid": 30976,
    "start_time": "2026-09-03T12:20:31Z",
    "first_hot": "2026-09-03T14:00:00Z",
    "last_hot": "2026-09-03T14:25:00Z",
    "hits": 6,
    "name": "python.exe",
    "cmdline": "python ... tests/test_app.py"
  }
}
```

Watcher запускается каждые:

`5 minutes`

Для каждого процесса:

* hot sample → `hits += 1`;
* cold sample → история sustained-spin сбрасывается;
* процесс исчез → запись удаляется;
* тот же PID с другим `StartTime` → считается новым процессом.

Процесс признаётся `sustained-spin`, если:

```text
hits >= 6
AND
now - first_hot >= 30 minutes
```

Нагрузка должна быть последовательной.

Если между hot samples появился cold sample, серия считается прерванной.

## 5. Orphan Detection

Проверяется:

`ParentProcessId`

Процесс считается кандидатом в orphan, если parent:

* отсутствует;
* завершён;
* недоступен как существующий процесс.

Но SAISPIN должен учитывать PID reuse.

Если процесс с указанным Parent PID существует, необходимо проверить его:

* `StartTime`;
* где возможно — имя процесса;
* где возможно — command line / launcher identity.

Если Parent PID уже принадлежит совершенно другому, более новому процессу, нельзя считать его настоящим parent только из-за совпадения PID.

Главное правило:

> Наличие живого процесса с таким же PID ещё не доказывает сохранность исходной parent-child связи.

## 6. Decision Matrix

| Orphan | Sustained Spin | Auto-Kill | Действие     |
| ------ | -------------- | --------- | ------------ |
| Нет    | Нет            | любое     | IGNORE       |
| Да     | Нет            | любое     | IGNORE       |
| Нет    | Да             | любое     | ALERT        |
| Да     | Да             | false     | ALERT        |
| Да     | Да             | true      | ALERT + KILL |

Ключевой safety invariant:

> **Non-orphan process никогда не должен автоматически завершаться SAISPIN.**

Даже если он часами грузит одно или несколько ядер.

Это может быть полностью легитимный:

* pytest;
* compiler;
* CMake;
* renderer;
* encoder;
* AI worker;
* build process;
* indexing task.

---

## 7. Pure Decision Engine

OS-independent logic вынести в:

`Scripts/saispin_logic.py`

Основной интерфейс:

```python
decide(history, sample, auto_kill=False) -> Decision
```

Результат:

```text
IGNORE
ALERT
KILL
```

Логика должна быть чистой:

* никакого PowerShell;
* никакого WMI;
* никакого Task Scheduler;
* никакого process termination;
* никакого tray UI.

Python-модуль отвечает только за решение по предоставленным данным.

Это позволяет тестировать критическую safety logic без реальных процессов.

## 8. Notifications

Использовать существующую notification infrastructure SAITULS.

Предпочтительно переиспользовать механизм из:

`tests/notify_alerts.cs`

SAISPIN должен отправлять tray alert и одновременно записывать событие в log.

Пример:

```text
SAISPIN: sustained CPU process detected

PID: 30976
Process: python.exe
CPU: 97% core
Duration: 34m
Orphan: YES
Mode: DRY-RUN
Command: python ... tests/test_app.py
```

Для kill:

```text
SAISPIN: orphan spin terminated

PID: 30976
Process: python.exe
CPU: 98% core
Duration: 41m
Orphan: YES
Action: KILLED
```

Command line необходимо обрезать до разумной длины, например:

`160–240 characters`

Полная command line при необходимости может сохраняться в structured log.

## 9. Logging

Каждый alert/kill должен создавать строку в SAISPIN log.

Минимальные поля:

```text
timestamp
pid
start_time
process_name
cmdline
cpu_percent
hot_duration
hits
orphan
decision
dry_run
```

Пример:

```text
2026-09-03T20:30:00+03:00 | PID=30976 | python.exe | CPU=98.1 | HOT=35m | ORPHAN=1 | ACTION=ALERT | python ...
```

Kill дополнительно логирует:

```text
kill_attempted=true
kill_confirmed=true|false
```

## 10. Auto-Kill Safety

Default:

```text
DryRun = true
```

Auto-kill должен включаться только явно.

Например:

```powershell
saispin_watch.ps1 -DryRun:$false
```

Перед kill повторно проверить:

1. PID существует;
2. `StartTime` совпадает с process identity из state;
3. процесс всё ещё orphan;
4. последний sample всё ещё hot;
5. process не находится в never-kill allowlist.

Только после этого:

```powershell
Stop-Process -Id $Pid -Force
```

После kill:

* небольшая пауза;
* повторная проверка PID + StartTime;
* убедиться, что исходный процесс действительно исчез.

Нельзя считать kill успешным только потому, что `Stop-Process` не выбросил exception.

---

## 11. Never-Kill Allowlist

SAISPIN должен иметь hard safety allowlist для критичных системных процессов.

Минимально:

```text
System
Idle
Registry
smss.exe
csrss.exe
wininit.exe
services.exe
lsass.exe
winlogon.exe
```

Также никогда автоматически не завершать основной процесс:

```text
Code.exe main process
```

При необходимости список можно расширять через config.

Allowlist влияет только на автоматическое завершение.

Подозрительный allowlisted процесс всё равно может быть залогирован или показан как alert, если это диагностически полезно.

---

## 12. Single Instance

Task Scheduler может случайно запустить новый экземпляр, пока предыдущий ещё работает.

SAISPIN обязан иметь single-instance protection.

Предпочтительно:

```text
named mutex
```

Например:

```text
Global\SAITULS_SAISPIN_WATCH
```

Если mutex уже занят:

```text
exit 0
```

Не создавать второй watcher.

Это обязательный invariant.

## 13. Task Scheduler

Installer:

`Scripts/Install-SaispinTask.ps1`

Создаёт задачу:

```text
SAITULS\SAISPIN
```

Поведение:

* запуск при logon;
* повтор каждые `5 minutes`;
* Hidden;
* переживает reboot;
* не запускает параллельные instances;
* working directory указывает на SAITULS;
* PowerShell запускается с корректным script path;
* default mode = dry-run.

Task Scheduler также должен быть настроен так, чтобы новый экземпляр не стартовал поверх уже работающего.

Script-level mutex остаётся обязательной второй линией защиты.

## 16. Error Handling

SAISPIN не должен падать из-за одного недоступного процесса.

Типичные ошибки:

* `Access denied`;
* процесс исчез между enumeration и sampling;
* command line недоступна;
* StartTime недоступен;
* WMI/CIM race;
* parent исчез во время проверки.

Каждая process probe должна быть изолирована через defensive error handling.

Принцип:

```text
cannot inspect one process
→ skip/process as unknown
→ continue watcher
```

Не превращать отсутствие доказательств в доказательство orphan state.

---

## 17. State Safety

State-файл должен обновляться атомарно.

Предпочтительная схема:

```text
write temporary file
→ flush
→ replace state file
```

Повреждённый state-файл не должен ломать watcher.

При невозможности прочитать state:

```text
start with empty history
log warning
continue
```

Никаких kill на основании повреждённой или частично восстановленной истории.

## 18. Acceptance Criteria

### Automated

Команда:

```text
python tests/test_saispin.py
```

Результат:

```text
all tests PASS
exit code 0
```

---

### Manual Dry-Run

Команда:

```powershell
.\Scripts\saispin_watch.ps1 -DryRun
```

Должна:

* просканировать процессы;
* выполнить два CPU samples;
* корректно обновить state;
* не завершить ни одного процесса;
* не падать на inaccessible processes;
* правильно классифицировать known hot/cold cases.

---

### Notification

При искусственно созданном sustained-spin:

* tray alert SAITULS появляется визуально;
* содержит PID;
* process name;
* CPU;
* duration;
* orphan status;
* command-line excerpt.

---

### Logging

Log должен содержать как минимум:

```text
PID
process identity
command line
CPU usage
hot duration
orphan status
decision
```

---

### Auto-Kill

В тестовом controlled case:

```text
orphan=true
sustained=true
auto-kill=true
```

SAISPIN:

1. повторно валидирует identity;
2. завершает процесс;
3. подтверждает его исчезновение;
4. пишет kill result в log.

False positive kill:

```text
0
```

---

## 19. Non-Goals

SAISPIN не является:

* общим task manager;
* antivirus;
* automatic CPU optimizer;
* memory cleaner;
* watchdog для всех медленных программ;
* инструментом для убийства процессов просто потому, что они долго работают.

Он решает узкую проблему:

> **обнаружение длительно spinning процессов, особенно потерявших управляющий parent lifecycle.**

---

## 20. Core Invariants

```text
1. One CPU spike never causes action.

2. Orphan alone never causes kill.

3. Spin alone never causes kill.

4. Automatic kill requires:
   orphan
   AND sustained-spin
   AND auto-kill enabled
   AND matching process identity
   AND not allowlisted.

5. PID alone is never process identity.

6. Non-orphan processes are never auto-killed.

7. Missing information must bias toward safety.

8. Default mode is dry-run.

9. Watcher must remain single-instance.

10. No kill may occur from stale history.
```

---

## SAISPIN in one sentence

**SAISPIN watches for processes that have lost their owner and kept pointlessly burning CPU, warns through SAITULS, and only kills them automatically when orphanhood and sustained spin are both proven.**
