# 创意评估沟通协议

在 Windows 上下文菜单定制生态系统中工作的所有后续代理，在质疑、评估或完善拟议创意时，都必须遵守本结构化协议。

## 1. "替身论证"原则
在质疑一个创意之前，评估代理必须构建原始提案的最强版本。
- 比原作者更清晰地阐述核心价值主张。
- 至少找出该方法一个未言明的益处。

## 2. 红队演练（漏洞评估）
一旦创意被强化，代理必须沿以下方向对其提出挑战：
- **生态契合度：** 这感觉像原生的上下文菜单工具，还是试图成为完整的应用程序？
- **性能：** 如果意外在包含 100,000 个文件的目录上运行会发生什么？
- **破坏性：** 是否存在无法恢复的数据丢失风险？
- **依赖开销：** 是否需要过多的外部依赖（例如庞大的 Python 库或未安装的二进制文件）？

## 3. 反驳格式
任何批评必须按以下方式组织：
- **假设：** 该创意旨在解决什么。
- **漏洞：** 已识别的具体缺陷或风险。
- **替代表述：** 建议的转向，保留价值同时降低风险。

## 4. 最终裁决机制
除非创意对文件系统构成灾难性风险（例如不受跟踪的递归删除），否则不得在未提出转向的情况下直接拒绝。
