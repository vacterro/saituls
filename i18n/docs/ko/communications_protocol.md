# 아이디어 평가를 위한 커뮤니케이션 프로토콜

Windows 컨텍스트 메뉴 사용자 정의 생태계에서 작업하는 모든 후속 에이전트는 제안된 아이디어에 이의를 제기하거나, 평가하거나, 개선할 때 이 구조화된 프로토콜을 준수해야 합니다.

## 1. "스틸맨" 원칙
아이디어에 이의를 제기하기 전에 평가 에이전트는 원래 제안의 가장 강력한 버전을 구성해야 합니다.
- 핵심 가치 제안을 원저자보다 더 명확하게 표현합니다.
- 접근 방식의 언급되지 않은 이점을 하나 이상 식별합니다.

## 2. 레드팀(취약성 평가)
아이디어가 강화되면 에이전트는 다음 벡터를 따라 이의를 제기해야 합니다.
- **생태계 적합성:** 네이티브 컨텍스트 메뉴 도구처럼 느껴지는가, 아니면 완전한 애플리케이션이 되려고 하는가?
- **성능:** 100,000개의 파일이 있는 디렉터리에서 실수로 실행되면 어떻게 됩니까?
- **파괴성:** 복구할 수 없는 데이터 손실 위험이 있습니까?
- **의존성 부담:** 과도한 외부 의존성(예: 거대한 Python 라이브러리 또는 설치되지 않은 바이너리)이 필요합니까?

## 3. 반박 형식
모든 비판은 다음과 같이 구성되어야 합니다.
- **가설:** 아이디어가 해결하려는 것.
- **취약성:** 식별된 특정 결함 또는 위험.
- **대안적 공식화:** 가치는 유지하면서 위험을 완화하는 제안된 전환.

## 4. 최종 판정 메커니즘
아이디어는 파일 시스템에 대한 치명적 위험(예: 추적되지 않는 재귀 삭제)을 초래하지 않는 한, 전환을 제안하지 않고 무조건 거부해서는 안 됩니다.
