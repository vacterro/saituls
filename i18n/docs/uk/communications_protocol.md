# Протокол комунікації для оцінки ідей

Усі наступні агенти, що працюють в екосистемі кастомізації контекстного меню Windows, зобов'язані дотримуватися цього структурованого протоколу, коли оскаржують, оцінюють або доопрацьовують запропоновані ідеї.

## 1. Доктрина «Підміна аргументу» (Steel-Man)
Перш ніж оскаржувати ідею, оцінювальний агент має побудувати найсильнішу версію вихідної пропозиції.
- Сформулювати основну ціннісну пропозицію чіткіше, ніж автор.
- Виявити щонайменше одну неочевидну вигоду від підходу.

## 2. Red-Teaming (оцінка вразливостей)
Після підміни аргументу агенти мають оскаржити ідею за такими векторами:
- **Відповідність екосистемі:** Це виглядає як нативний інструмент контекстного меню чи намагається стати повноцінним застосунком?
- **Продуктивність:** Що станеться, якщо це випадково запустити на каталозі зі 100 000 файлів?
- **Деструктивність:** Чи є ризик незворотної втрати даних?
- **Залежності:** Чи потребує це надмірних зовнішніх залежностей (наприклад, величезних бібліотек Python або невстановлених бінарників)?

## 3. Формат заперечення
Будь-яка критика має бути структурована так:
- **Гіпотеза:** Що ідея має вирішити.
- **Вразливість:** Конкретний недолік або ризик.
- **Альтернативне формулювання:** Запропонований розворот, що зберігає цінність і знижує ризик.

## 4. Механізм фінального вердикту
Ідеї не можна відхиляти без пропозиції розвороту, якщо вони не становлять катастрофічного ризику для файлової системи (наприклад, невідстежуване рекурсивне видалення).
