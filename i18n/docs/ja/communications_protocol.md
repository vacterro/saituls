# アイデア評価のためのコミュニケーション・プロトコル

Windows コンテキストメニューカスタマイズのエコシステムで働くすべての後続エージェントは、提案されたアイデアに異議を唱え、評価し、洗練する際に、この構造化プロトコルに従わなければなりません。

## 1. 「スチールマン」の原則
アイデアに異議を唱える前に、評価エージェントは元の提案の最強版を構築しなければなりません。
- 核となる価値提案を原作者より明確に述べること。
- そのアプローチの、まだ語られていない利点を少なくとも1つ特定すること。

## 2. レッドチーミング（脆弱性評価）
アイデアを最強版にした後、エージェントは以下のベクトルで挑戦しなければなりません。
- **エコシステム適合性:** ネイティブなコンテキストメニューツールのように見えるか、それとも完全なアプリケーションになろうとしているか?
- **パフォーマンス:** 100,000ファイルのディレクトリで誤って実行されたらどうなるか?
- **破壊性:** 回復不能なデータ損失のリスクはあるか?
- **依存関係:** 過剰な外部依存関係（巨大なPythonライブラリや未インストールのバイナリなど）を必要とするか?

## 3. 反論の形式
あらゆる批判は次のように構成されなければなりません。
- **仮説:** アイデアが解決しようとしていること。
- **脆弱性:** 特定された具体的な欠陥またはリスク。
- **代替案:** 価値を維持しつつリスクを軽減する提案された転換。

## 4. 最終判定メカニズム
アイデアは、ファイルシステムへの壊滅的なリスク（例: 追跡されない再帰的削除）を伴わない限り、転換案を提示せずに却下してはなりません。
